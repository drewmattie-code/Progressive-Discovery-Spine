# Action menu — UI pattern for curated invocation

This is the UI manifestation of principle #9. The Action Menu is what makes "zero hallucination surface" actually true in production — the agent never picks parameters; the UI binds them.

## The pattern

Every entity in your UI surfaces a right-click (or long-press, or button click) **Action Menu**. The menu exposes a small set — six is the canonical number — of pre-parameterized actions. Parameters are bound from UI context, not generated by the agent.

```
┌─────────────────────────────────────────────┐
│ Supplier: Acme Components                   │  ← user right-clicks this row
│   Risk score: 72  ·  Open POs: 14           │
└─────────────────────────────────────────────┘
                    │
                    ▼
    ┌────────────────────────────────────┐
    │  1. Draft letter of acceptance     │   ← invokes draft_letter_of_acceptance
    │  2. Reconcile current rebate       │   ← invokes reconcile_rebate
    │  3. Project stockout cascade       │   ← invokes project_stockout_cascade
    │  4. Get risk scorecard             │   ← invokes get_supplier_risk_scorecard
    │  5. Search open POs                │   ← invokes search_open_pos
    │  6. Escalate to CFO                │   ← invokes escalate_to_cfo
    └────────────────────────────────────┘
```

The user picks one. The agent invokes the tool with parameters bound from the UI:

```ts
// User clicked "Reconcile current rebate" on the supplier row.
invokeTool("reconcile_rebate", {
  supplier_id: row.supplierId,            // bound from the row the user clicked
  period: currentPeriod(),                // bound from app state
  tenant_id: session.tenantId,            // bound from session
});
```

No parameter is invented by the model.

## Why six

Six is enough variety to cover the workflows users actually do on an entity. Beyond six the menu becomes a decision tree and users start scrolling. Below four feels thin. The exact number isn't sacred, but resist the temptation to add a seventh until you've removed something.

## How to pick the six

For each entity type, ask: **"What are the six workflows a user actually starts from this entity?"** The answers come from observation, not imagination. If your product is new, ship four obvious ones and let usage data tell you the next two.

Avoid actions that are too generic ("View details") and actions that are too specific ("Reconcile Q3 rebate against contract clause 14.b"). The first wastes a slot; the second belongs in the resulting workflow, not the menu.

## What this prevents

- **Wrong tenant.** `tenant_id` comes from `session`, not from the agent. Cross-tenant calls are structurally impossible.
- **Hallucinated IDs.** `supplier_id` comes from the row the user clicked. Cannot drift.
- **Wrong period / scope.** Time-based parameters come from app state, not from the model interpreting "current."
- **Free-form contract reference.** Bound from the supplier's active contract record at click time.

## What this still allows

- The agent does the **work** of the action — drafting the letter, computing the reconciliation, projecting the cascade. The model is doing what it's good at (composition, drafting, explanation), not what it's bad at (picking IDs from a 50,000-row table).
- The user reviews the agent's output before commit. The Action Menu fires the agent; the user signs off.

## Combining with natural-language entry (principle #10)

The two patterns are complementary, not competing:

- **Action Menu** is for *known* workflows on *known* entities. Low cognitive load, zero hallucination.
- **Natural-language entry** is for *novel* questions across the whole system. High flexibility, depends on `search_tools` retrieval.

Most enterprise UI work over time tends to migrate common questions from the NL bar into the Action Menu. That migration is healthy — it's the codification of usage patterns into a tighter affordance.

## Implementation notes

- Render menu items from a manifest, not hardcoded. Each entity type declares its 4–6 actions.
- Each action manifest entry includes: label, tool name, parameter-binding rules (from UI context), and an optional confirmation prompt for high-impact actions ("Escalate to CFO" should confirm).
- Track menu-item usage. The data tells you which actions to promote, demote, or remove.
- High-impact actions ("Escalate", "Refund", "Cancel order") should always require an additional confirmation step regardless of the user's role.
